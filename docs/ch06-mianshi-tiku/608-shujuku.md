# 数据库面试题

数据库面试题的火力集中在两处：事务（ACID + 隔离级别）和索引（B+ 树）。这两块吃透，剩下零散题各备一个骨架即可。下面以 MySQL 为默认语境，被问到时主动说明自己熟悉哪家的实现，比泛泛而谈强。

## 事务与隔离级别：必考双连

**ACID**：骨架：原子性（事务全做或全不做，靠 undo log 回滚）、一致性（事务前后完整性约束不被破坏，是其余三者共同保证的目的）、隔离性（并发事务互不干扰，靠锁和 MVCC）、持久性（提交即永久，靠 redo log）→ 加分点：说出 undo/redo log 和 A、D 的对应关系，多数人只会背四个词。

**隔离级别与三类读问题**：骨架：脏读（读到别人未提交的数据）→ 不可重复读（同一事务两次读同一行结果不同，针对 update）→ 幻读（两次范围查询行数不同，针对 insert）→ 四个级别逐级堵漏：读未提交全都有、读已提交解决脏读、可重复读再解决不可重复读、串行化全解决但并发最差 → MySQL 默认可重复读。

追问与陷阱：可重复读怎么对付幻读——临键锁（间隙锁 + 行锁）锁住记录之间的空隙，禁止插入，这是 MySQL 对标准 SQL 的增强，答出「间隙锁」三个字就高了一档；三种读问题各配一个业务例子（余额、报表），给例子是区分背书和理解的分水岭。

**MVCC**：骨架：每行带版本链（undo log），事务按自己的快照读可见版本，读不加锁、读写不冲突。追问 MVCC 和锁的关系——MVCC 解决读-写冲突，写-写还是要靠锁。

## 索引：B+ 树的主场

**主问题：为什么索引用 B+ 树而不用哈希表或二叉树？**

骨架：二叉树/红黑树太高，磁盘 I/O 次数等于树高，矮胖的 B+ 树三四层撑千万数据 → 哈希虽然等值查询 O(1)，但不支持范围查询和排序，且存在冲突 → B+ 树叶子节点成有序链表，范围查询扫链表即可 → 非叶节点只存键不存数据，单页能放更多键，扇出更大树更矮。

**聚簇 vs 非聚簇**：骨架：聚簇索引叶子存整行数据（InnoDB 主键索引），表本身就是按主键组织的 B+ 树；二级索引叶子存主键值，查到后要回表 → 引出覆盖索引：查询的列全在索引里就不用回表，SQL 优化的常用抓手。

追问与陷阱：为什么建议用自增主键——随机主键（如 UUID）插入会页分裂，写放大；最左前缀原则——联合索引 (a,b,c) 只有从 a 开始连续命中才能走索引；什么情况索引失效——对列做函数运算、隐式类型转换、前导模糊匹配 LIKE '%x'。

失分点：只答「B+ 树查询快」说不出和磁盘 I/O 的关系。索引设计的一切出发点是「磁盘读一次很贵，减少读的次数」，这条主线丢了，后面的追问全接不住。

## 范式与表设计

**三范式**：骨架：1NF 字段原子不可再分 → 2NF 消除对主键的部分依赖（非主属性要依赖整个主键）→ 3NF 消除传递依赖（非主属性之间不互相依赖）→ 反范式化：适当冗余换查询性能，减少 join，用一致性问题做代价。

追问：什么时候该反范式——读多写少、join 代价高的场景（如报表统计），答出「范式是设计起点不是教条」即可。

## 锁与 SQL 优化

**乐观锁 vs 悲观锁**：悲观锁假定冲突常发，先加锁再操作（select for update）；乐观锁假定冲突少，提交时校验版本号，失败重试 → 读多写少用乐观，写冲突频繁用悲观。

**SQL 优化清单**：骨架四条——看执行计划 explain（重点看 type 是否走索引、rows 扫描量）；建对索引（联合索引列序、覆盖索引）；改写 SQL（避免 select *、大分页改游标、or 改 union）；必要时加缓存或分库分表。追问「线上一条 SQL 慢，怎么排查」——按这个清单从 explain 开始说，有条理比结论重要。

**零星高频**：连接三兄弟——内连接只保留匹配行，左连接保左表全量右表补 NULL；关系型 vs 非关系型——结构化强一致 vs 灵活 schema、水平扩展，举 Redis/MongoDB 的适用场景各一句；数据库连接池为什么存在——建连开销大（TCP + 认证），池化复用。

这门课的题总量不大，适合面试前一晚收尾复习：把隔离级别那张阶梯表和 B+ 树的三个理由过一遍，其余题凭骨架现场展开即可。
